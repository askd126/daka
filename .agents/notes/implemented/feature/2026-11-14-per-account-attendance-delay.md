# Agent Note: 青龙打卡按账号和班次独立延时

Status: implemented

## Problem

上、下班任务各自只抽取一次随机等待，等待结束后串行处理全部账号。无法给不同的人设置各自的延时，而且若在串行循环内加等待，后面账号的实际执行时间会累加上前面账号的等待和处理时间。

## Decision

`HIK_DAKA_DELAY_MORNING` 和 `HIK_DAKA_DELAY_EVENING` 分别为上、下班延时，使用与 `HIK_DAKA_TOKEN` 相同的编号后缀。值是 0 至 7200 的整数秒，或 `min-max` 的闭区间；配置 `0` 表示立即处理。未配置时各账号独立使用原任务 `--delay` 的默认上限抽样，定时任务的开始时间不变。非法值只令对应账号失败，错误只显示变量名和正确格式，不回显原值。

节假日检查通过后，所有账号各自启动定时器。等待结束后才验证 Token、查询当日状态、按原规则提交和恢复过期 Cookie。并发任务按原编号顺序返回结果，个人通知仍随账号完成发送，系统汇总等待全部账号完成后发送一次。`--check` 验证延时配置但不等待，也不提交、推送或写打卡历史。

## Alternatives considered

在原串行循环中等待只需小改动，且海康请求不会并发，但后续账号的实际延时会随前序账号等待、重试甚至推送延迟而漂移。给每个账号创建独立的青龙定时任务也能隔离等待和故障，但会随账号数增加任务并拆散管理员总推送。采用一个班次任务内的独立定时器保留这两个边界。

## Consequences

不同账号可能同时到期并发请求；相同的固定值或随机结果可以重合。脚本等待的是开始处理时间，实际提交还要经过原有考勤校验，配置者需留出考勤窗口余量。延时绑定原有 Token 变量名，正常续期不需要修改延时；更换变量编号时要同步延时配置。
